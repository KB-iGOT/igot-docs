Blended Program
Instructor-led learning that mixes self-paced online content with scheduled classroom sessions — batches with seat limits, an approval step, session attendance and assignments.
Category  Blended Program Route  /app/toc/:programId Workflow  blendedprogram ✓ Verified from repos · 4.8.41 releases · boundaries noted

What it is

A Blended Program pairs self-paced online content with classroom sessions, run in batches. A Karmayogi picks a batch that still accepts enrolments and has room, completes any entry steps the batch asks for, and requests a seat. A Program Coordinator, an MDO admin, or both in a fixed order approve the request — or a coordinator nominates the learner directly, or the learner scans a self-enrolment QR in the room. Once the batch is running the learner works through the online content, attends the sessions, hands in assignments and earns the batch certificate.

Batches & seats

Each batch has its own dates, enrolment window and seat limit. The page warns when seats are running low and when a batch or every batch is full.

Approval or direct entry

A seat is a request until an approver says yes. Coordinators can nominate learners straight into a batch, and a QR code can let people in the room enrol themselves.

Sessions, attendance & assignments

Classroom sessions show date, time, handouts and links. Attendance is marked by the coordinator, or by the learner scanning the session QR on the mobile app at the venue. Assignments are handed in as PDFs and evaluated with marks and feedback.

How a Karmayogi experiences it

1 · PICK A BATCH

Opens the program and chooses a batch that is open and has seats

2 · ENTRY STEPS

Pre-requisites, a profile form and a short survey, if the batch asks for them

3 · REQUEST

Confirms the batch dates; a schedule clash with another batch is refused

4 · APPROVAL

Waits for the coordinator and/or MDO admin; can withdraw while pending

5 · LEARN & ATTEND

Self-paced content, sessions, assignments, then the certificate

Course
The standard self-paced unit of learning — one-click enrolment, node-by-node progress, Karma Points and a certificate on completion.
Category  CourseRoute  /app/toc/:courseId✓ Verified from repos · Aug 2026

What it is

The building block of the Learning Hub. Unlike a Blended Program, a Course has no approval workflow: tapping Enrol writes the enrolment directly and the course lands in My Learning at 0%. Progress is tracked per content node, Karma Points accrue on completion events, and a certificate issues when every mandatory node is complete.

Instant enrolment

One call, no approvers — the contrast that defines every other category.

Node-level progress

Every video, PDF and quiz reports its own state; the course rolls them up.

Rewards

Karma Points and certificates hang off the same completion signal.

Learning Pathway
A guided, multi-stage journey — milestones of courses and checkpoints that unlock one at a time.
Category  courseCategory = "Learning Pathway"Status  thin backend — content-model overlay, no dedicated service

What it is

A pathway looks like a course laid out as a staircase of up to five milestones, each a small bundle of courses (some mandatory, some optional) ending in its own checkpoint assessment. The next milestone stays locked until the current one's mandatory courses are done and its checkpoint is passed — and every one of those locks is worked out on the learner's own device from ordinary course-progress data, not fetched from a dedicated "pathway progress" API.

Honest gap: Learning Pathway is not a bespoke backend feature — it is an ordinary content/collection node distinguished only by courseCategory = "Learning Pathway", with milestones embedded as opaque JSON. There is no attempt-limit/cool-off enforcement anywhere, and several pieces (access control rules, discovery inclusion, certificate/QR/karma issuance) depend on external services or remote config not present in the four repos traced. Treat this page as thorough but bounded by that scope.
Content overlay, not a service

Every write reuses the generic Content CRUD actors; only the enriched read is pathway-aware.

Client-derived unlock

Web and mobile each independently recompute milestone lock state — no server push, no shared code between them.

Per-milestone achievement

Finishing a milestone can award its own certificate, not just one at the very end.

Peer Validation
A named colleague, not a machine, has to approve a course completion before it counts.
Trigger  30-60 days after completion✓ Verified from 8 repos · Sept 2026

What it is

Some courses come with a peer-validation survey attached by the department. Days after a Karmayogi finishes such a course, they're prompted to answer a short survey, optionally attach proof, and name two or three peers who can vouch for the work. Each peer reviews independently and approves or rejects — a one-shot, unchangeable decision. There is no owning backend service: the survey, the notification/status tracking, and the reporting each live in a separate system, correlated only by shared IDs.

Terminal by design

A rejection is a dead end today — no resubmission path exists.

No escalation

An unreviewed request just sits — nothing reminds or reassigns the peer.

Display-only expiry

"Expired" is calculated when viewed, never persisted — the underlying row can stay pending indefinitely.

CHS
A nightly batch pipeline — not a page or a button — that turns raw platform activity into karma points, badges, leaderboards, compliance reports and the BI warehouse.
Repo  cb-core-data

What it is

CHS is the platform's batch analytics pipeline — the jobs that turn raw activity data into karma points, badges, leaderboards, compliance reports and the BI warehouse. It runs nightly, unattended, and shapes what MDO admins, BI/Looker consumers, the live dashboard, and downstream notification systems see.

No incremental sync, anywhere

Every warehouse write is a full truncate-and-reload on every run — simple to reason about, but a table is genuinely empty (not stale) during a failed or slow sync.

Four very different consumers

AI CBP Tool
Turns a department's own Work Allocation Order and other source documents into a designation-by-designation Capacity Building Plan — role profile, competencies, and a course list — reviewed, approved and published by an MDO admin.

Overview of the CBP Tool

The AI CBP Tool under Mission Karmayogi is being transformed from an isolated prototype into an enterprise-grade, governance-aligned and automated competency ecosystem, integrated with the MDO Portals, the iGOT Platform and SPV workflows.

Key architectural & functional pillars

Document Ingestion & Multi-Document Persistence
  • Persistence: Appends newly extracted roles without overwriting previously parsed documents or session history across multiple uploads.
  • Work Allocation Order (WAO) Priority: Gives the highest AI weightage to official WAOs for deriving designations, roles, responsibilities, activities and competencies.
  • Standardized Templates: Provides downloadable standardized Word and PDF templates to maximize OCR/NLP extraction fidelity.
Accurate Role Mapping & KCM Compliance
  • Strict Boundary: Behavioural and Functional competencies must originate strictly from the Karmayogi Competency Model (KCM) catalogue; out-of-model suggestions are filtered.
  • Designation Hygiene: Eliminates improper merging of similar designations, for example treating "Senior Section Officer" and "Section Officer" as distinct entities.
  • Hierarchy Definition: Configurable L1 to L4 designation seniority sorting to structure the final CBP.
iGOT Designation Master Matching & SPV Governance
  • Hybrid Matching: Fuzzy matching (92% confidence threshold or higher) aligns extracted designations with the canonical iGOT Designation Master.
  • Two-Track Flow:
    • Matched designations: move directly to CBP generation and MDO approval.
    • Unmatched designations: the author can manually override through a searchable dropdown, or trigger an SPV Admin workflow to add the missing designation to the central master.
Next-Generation Course Recommendation Engine
  • Multi-Factor Weighted Ranking: Replaces raw embedding similarity with a 100-point weighted scorecard: Competency match 30%, Role context 20%, Domain relevance 15%, Provider match 10%, Org match 10%, Difficulty 5%, Metadata 5%, Outcomes 5%.
  • Target Mix by Seniority:
    • Group A / B (Senior / Strategic): 50% Domain, 25% Behavioural, 25% Functional.
    • Group C / D (Field / Operational): 40% Domain, 30% Behavioural, 30% Functional.
  • Business Rules & Constraints: A cap of 50 total learning hours per recommendation set; mandatory default course injection (via locked DO_IDs); public courses removed or disabled; manual course additions default to 90% relevance.
Approval Governance & iGOT Publishing
  • Lifecycle Statuses: Draft → Pending Approval → Approved / Approved & Published / Rejected / Partially Published.
  • MDO Approval: Review by mapped MDO Leaders and Admins, with inline editing and mandatory review remarks.
  • iGOT Publishing: Published training plans (AI CBP – Non APAR for cycle 2026–2027) surface on myiGOT within about 6 hours and notify learners with matching designations.
Scale, User Management & Backend Automation
  • Nationwide Deployment: Backend scripts, run under a dedicated service account, automate batch generation and cross-department copying by designation clusters for about 1,100 MDOs.
  • Human-in-the-Loop Validation: An AMS team CSV export and validation loop runs before full-scale publishing.
  • Access & Inclusivity: Keycloak SSO with RBAC, full audit logging, and multilingual CBP export across 11 Indic languages.

Step 1
Secure login & context setting

Sign in with Keycloak SSO and choose the organisation the work is scoped to.

Document ingestion & template standardization

Download the template, upload one or more orders, and watch roles accumulate with their sources.

Step 3
AI-driven role & competency generation

The AI extracts designations, weights Work Allocation Orders first and keeps competencies inside KCM.

  • Designation Extraction: The AI extracts all designations without conflating titles; "Under Secretary" is not merged with "Deputy Secretary".

Course recommendation review & curation

    • Operational staff (Group C / D) receive about 40% operational domain courses.

  • Editing & Adding Courses:
    • The author can delete irrelevant courses or search the iGOT catalogue to add modules manually.
    • Any manually added course automatically receives a 90% relevance score, so it never shows 0%.
    • The system enforces a 50-hour total learning cap; if it is exceeded, the author is prompted to trim course durations before proceeding.
    • After saving or editing inline, the UI scrolls back to the active section.

Plan preview, language selection & submission

Preview the CBP in any of 12 languages, then send finalized designations for approval.

  • Check Validation: Checkboxes next to designations become active only after course recommendations are generated and saved.

    • The author checks off finalized designations and clicks "Send for Approval".

MDO approval & revision loop

Track the request, revoke it while pending, and resubmit after a rejection with the reviewer's remarks.

  • Author Tracking: The author tracks progress in the Approval Requests Dashboard: Draft, Pending Approval, Approved, Rejected, Partially Published.

  • Approver Interaction:
    • If the MDO Leader approves, they define the official Training Plan Name and Target Completion Date (for example 31 March 2027).
    • If the MDO Leader rejects, the author receives an email notification with specific rejection remarks, and can adjust competencies or courses and resubmit.
Step 8
Publishing & monitoring impact

Approved plans reach myiGOT within about 6 hours; the dashboard tracks coverage and training gaps.

  • Pushed to iGOT: Once approved, the training plan is published to the MDO Portal and the Learner Portal (myiGOT). Within about 6 hours, mapped government officials see the CBP prominently on their myiGOT home screen.
  • Executive Dashboard: The author visits the AI CBP Dashboard to track:
    • Total CBPs created across their department.
    • Gap Analysis: competencies without matching iGOT courses, highlighting training deficits where new courses should be commissioned.
    • Unique designations mapped versus remaining departmental roles.

Search
Platform-wide search: an Elasticsearch-backed content/people/community search fronted by every portal and the mobile app, plus an independent LLM keyword-extraction step that two of five clients call before they search.
Repos  nlp-search · knowledge-platform · knowledge-platform-jobs · sunbird-cb-uiproxy · sunbird-devops · +5 frontends✓ Verified from 10 repos · Sept 2026

What it is

A user types a query into one of five clients. On the learner web portal and the mobile app, the client first sends the raw query to nlp-search, which uses Gemini to extract a ranked keyword list — the top-priority keyword, not the user's literal text, becomes the actual search term. The three admin/authoring portals skip this step and search on the raw query. Whichever term is used, the client calls a versioned content-search endpoint that lands on knowledge-platform's search-service, which builds an Elasticsearch query against the compositesearch index. That index is kept current by a completely separate pipeline — a Kafka-driven Flink job in knowledge-platform-jobs — not by search-service itself.

Honest gap: two backends never call each other, and are stitched together only client-side, only in two of five clients. Kong's own routing config — what host /nlp/search and /search/* actually resolve to — lives outside all ten traced repos. See the HLD tab for the full topology and the rest of the honest gaps.
Two backends, stitched only client-side

nlp-search (LLM keyword extraction) and search-service (Elasticsearch) never call each other — confirmed by a repo-wide grep for "nlp" turning up zero hits in either knowledge-platform repo.

NLP is opt-in per client, not a platform rule

Only the web portal's search-v3 and the mobile app call nlp-search first. The three admin-facing portals search on raw text.

Indexing is a separate pipeline entirely

search-service is read-only against Elasticsearch. A Kafka-driven Flink job in knowledge-platform-jobs does all the writing, on a completely independent failure/retry path.

Unenrollment of Courses
A learner-initiated withdrawal from a course/batch — one boolean flip on the same generic enrolment record enroll writes, blocked once the course is completed, and wired up very differently depending on which client the learner is standing in.
Endpoint  POST /v1/course/unenrollClient parity  mobile full UX · web has none for a plain course✓ Verified from 7 repos · Sept 2026

What it is

A learner who wants out of a course hits POST /v1/course/unenroll, which refuses if the batch has ended, if they aren't actually enrolled, or — the one hard business rule — if they've already completed the course. Otherwise it flips active to false on the enrolment row and its per-batch lookup row. On mobile this has a full, deliberate UX: a confirmation sheet with a mandatory checkbox, then a mandatory reason-picker, before the call is made. On web, no such UI exists for a plain course at all — the only "unenroll"-labelled action there is withdrawing a still-pending blended-program enrolment request, a structurally different feature.

Honest gap: a whole second notification system (in-app, Kafka-driven, subcategory CONTENT_UN_ENROLLED) is fully built with message templates in cb-notification-service/cb-notification-wrapper, but nothing anywhere in the ten repos scoped to this feature ever calls it — only the older actor-native email path is actually live.
No dedicated unenroll service

Reuses the exact same actor, DAO layer, and Cassandra tables as enroll — the only difference is which validation branch runs and which single field gets written.

Mobile vs. web parity gap

Mobile built a complete unenroll UX for a plain course; web built none — its only unenroll action is the unrelated blended-program workflow withdrawal.

Completion blocks it, certification doesn't

Unenroll is refused once course-completion status is COMPLETED, but nothing checks whether a certificate was actually issued.

Impact-disclosure sheet, checkbox required to continue

Moderated Content
Two unrelated systems sharing one name: an MDO-restricted courseCategory/secureSettings visibility scheme for Moderated Course/Program/Assessment riding on the generic Sunbird review workflow, and an independent ML text-profanity check on discussion posts.
Categories  Moderated Course/Program/AssessmentScoping  secureSettings.organisation + isVerifiedKarmayogi✓ Verified from 13 repos · Sept 2026

What it is

"Moderated" is a courseCategory value (Moderated Course/Moderated Program/Moderated Assessment) on ordinary Sunbird course content, restricted to specific MDOs via a secureSettings.organisation array and optionally a secureSettings.isVerifiedKarmayogi toggle — enforced as an Elasticsearch nested-query filter inside knowledge-platform's search actor, not just a client-side hide. Authoring rides the same generic Draft→Review→Live workflow every other content type uses, gated by the CONTENT_REVIEWER role. A structurally unrelated feature also called "moderation" — automatic text-profanity screening of discussion posts — runs through a separate transformer-based service, called asynchronously from cb-discussion-service; a flagged post is soft-hidden from listings, not deleted.

Honest gap: of the moderation-notification types the platform's own NotificationSubCategory taxonomy is clearly built to support — course/program submitted-for-review, approved, rejected — only the discussion-profanity alert (PROFANITY_CHECK) has a locatable producer across all 13 repos traced, and even that one has a payload-shape mismatch with the endpoint it calls that was never confirmed to work at runtime.
No dedicated moderated-content service

It's a courseCategory value plus a secureSettings field on the generic content schema — no separate table, schema, or approval API exists beyond that.

Enforced at the search engine, not just the UI

SearchProcessor's nested Elasticsearch query on secureSettings.organisation means a client skipping the filter still can't retrieve out-of-org content.

Two "moderation" systems, zero shared code

MDO-restricted course/program visibility and ML discussion-post profanity checking live in different repos, different data models, different notification paths.

User Onboarding
How a person gets an account — public sign-up, a department's registration link or QR code, an admin adding them, or government single sign-on — and the admin steps behind it. Registering submits a request; the account is created afterwards.
Routes  /public/signup · /crp/:id/:orgId · /public/welcome · /app/home/onboardingBulk CSV  see Bulk Registration✓ Verified from 14 repos · Oct 2026

What it is

A new Karmayogi starts at the sign-up page (or the app's intro screens), chooses their ministry or state, their organisation and their designation, proves they own their email address and mobile number with one-time codes, and submits. What they have sent is a request, not an account. If they came in through their department's registration link or QR code, or their email domain is already approved, the account is created straight away and an activation email follows; otherwise the request waits for approval first. Department admins can add a person directly, and people with a government single sign-on identity are created on their first login and sent to a short welcome form.

Honest gap: the approval states that decide who approves a held registration are loaded from a platform setting at run time, so they cannot be read from the code. What sends a user to the welcome form after first login is also not in the repositories traced.
A request first, an account later

Submitting the form answers "accepted" and stores a registration record; the account, organisation, role and activation email are produced afterwards in the background.

A link is a pass

A department's registration link replaces both the email-domain check and the approval step — and each department has only one active link at a time.

A partner/external-content ecosystem layered alongside the native Course pipeline — third-party providers are registered, licensed, and have their catalogs ingested through a separate storage, enrollment and entitlement stack that only loosely interoperates with native platform content.

What it is

A content partner is onboarded (directly by an admin, or self-registered then approved), its catalog is ingested by uploading an Excel/CSV file that a dedicated ingestion service transforms per-partner and indexes into its own store — entirely separate from the platform's native content graph. A curator reviews, competency-tags and publishes each course; a learner discovers it via a provider directory or a spotlight card, opens a dedicated CIOS detail page, and enrolls through a third, independent enrollment engine that enforces per-partner license caps before writing the enrollment.

Honest gap: no single service owns "is this user enrolled in this partner course." Three separate content stores

cb-pores-service (partner master data), cios-content-service (ingested catalog) and cb_external_enrollment_service (a third local mirror) each keep their own copy of "CIOS content," with no shared code between them.

AI Assessment Tool
Turns a course's PDFs and video subtitles — or just a set of Karmayogi Competency Model selections, with no course at all — into a ready-to-publish, multi-question-type, multilingual assessment, generated by Google Gemini via Vertex AI.
Repos  ai-assessment-service · sunbird-cb-uiproxy · sunbird-cb-workflow · sunbird-devopsSelf-described as  assessment-generator✓ Verified from 4 repos · Sept 2026

What it is

A user holding the AI_ASSESSMENT_CREATOR role — granted only after an SPV Publisher approves their request in a separate workflow service — calls the generate API through the Karmayogi gateway. The service validates the caller's JWT and role, checks a Postgres-backed cache for an identical prior request (returning it instantly, or cloning another user's matching result), and otherwise queues a Kafka job. A worker fetches the course's PDFs and video captions, builds one large Gemini prompt combining the source content with a cached Karmayogi Competency Model reference dataset, and calls Vertex AI with a strict JSON schema. The result can be downloaded as JSON, one of two CSV schemas, a font-embedded PDF, or a DOCX.

Honest gap: no UI trigger for this service was found in the platform's own authoring app (sunbird-cb-creationportal) or in cbp-ai-ui — both were checked and confirmed to have no code-level connection to this feature. The only client-side code found is this repo's own bundled Streamlit reference UI.
Identical requests are cloned, not regenerated

A matching request from a different user returns that user's already-generated content instantly — a deliberate cost-saving design, not a bug.

One prompt template drives 25 combinations

All 5 assessment types × 5 question types share a single template, with type-specific behavior expressed as conditionally-included instruction blocks.

AI Tutor

Overview

iGOT’s AI Tutor on the Learner Portal.

The initiative introduces an RAG-based, agentic conversational assistant capable of answering course-specific queries, directing users to exact video segments and reference materials, tailoring answers to specific pedagogical styles (such as Storytelling), while strictly respecting content authorization and gathering structured user feedback.

Core Functional Pillars

1. Core AI Tutor
  • Location: Accessible from the Course Table of Contents (TOC), Resources, and Player pages.
  • Enrollment Gating: The chatbot is only enabled for enrolled learners; un-enrolled learners are prompted to enroll directly within the bot interface before conversation begins.
  • RAG Retrieval: Searches vectorized CC BY 4.0 content (Courses & Programs), using NLP over titles, summaries, descriptions, meta tags, competencies, and video transcriptions.
  • Deep Linking: Generates responses linking directly to specific content IDs and segmented video timestamps.
  • Guardrails: Disabled during assessments; gracefully deflects non-learning/unrelated queries.
2. Personalized Learning Styles
  • Style choice: Allows learners to explicitly select Storytelling as their learning style (alongside Socratic mode).
  • Narrative tailoring: The AI Tutor tailors its explanations, examples, and tone to convey course concepts narratively.
3. Security & Access Governance
  • Query-time checks: Dynamically evaluates user permissions, roles, and course enrollments at query time.
  • No leakage: Ensures restricted or role-specific content is never surfaced in AI responses to unauthorized users across both AI Global Search and the AI Tutor.
4. Quality Evaluation & Feedback Loops
  • Feedback system: Integrates Thumbs Up / Thumbs Down feedback across search and tutor responses (RLHF / telemetry).
  • Thumbs Down: Mandatory comments to capture why the answer was unhelpful or inaccurate.
  • Thumbs Up: Comments optional.

Chatting with the AI Tutor

Step 01 · Learner
Open the tutor and connect

Start a chat in your chosen learning style; the tutor greets you once the connection is made.

Steps

  1. Open the AI Tutor from the Course TOC, Resources or Player page (it is available to enrolled learners).
  2. Choose a learning style: Socratic, Storytelling, or plain answers.
  3. Your signed-in session is used to connect; no separate login is needed.
  4. Wait for the welcome message from the tutor before you type.

What you get

A welcome message in the tone of the chosen style, confirming the chat is ready.

Step 02 · Learner
Ask a question

Type a question about the course content; the tutor can use your earlier messages in the same chat.

Steps

  1. Type your question in the chat box and send it.
  2. Keep follow-up questions in the same chat so the tutor can use the conversation so far.
  3. Optionally keep the question focused on one course or folder of content.

What you get

The tutor searches the course material that matches your question and prepares an answer.

Step 03 · Learner
Read the answer and its sources

Every answer comes with the content items it was drawn from, so you can go back to the source.

Steps

  1. Read the answer in the chat window.
  2. Check the sources listed with the answer: each shows the content name, its type and how closely it matched.
  3. Open a source to revisit that part of the course.
  4. The tutor marks the end of the reply so you know it has finished.

What you get

An answer in your chosen style plus the matching course content it came from.

Step 04 · Learner
If something goes wrong

A short, friendly message is shown instead of a technical error.

Steps

  1. If the tutor cannot answer, a friendly message appears in the chat.
  2. Send your question again, or rephrase it.
  3. If the connection drops, reopen the tutor and start again.
Step 05 · Learner
End a chat and revisit past chats

Close a session when you are done and look back at earlier conversations.

Steps

  1. End the chat when you have finished; the session is marked as ended.
  2. Open your chat history to see earlier conversations grouped by chat.
  3. Each chat lists your questions and the tutor’s answers with the time they were sent.

What you get

A saved, per-chat record of questions and answers.

Two parallel competency taxonomies — a real CRUD+review service (frac-backend) almost nothing calls, and a mirror inside Knowledge Platform (kcmfinal_fw) that most of the platform calls instead — plus the Passbook, browse/search and org-designation-mapping surfaces built on top.

What it is

There turn out to be two competency taxonomies, not one. frac-backend is a real Spring Boot service — one generic DataNode model for Competency/Role/Activity/Position/etc., MySQL + Elasticsearch storage, and a genuine two-tier (L1/L2) review workflow before a node counts as verified. Almost nothing in this trace calls it directly except sunbird-cb-uiproxy's two hand-written FRAC routers and Work Allocation verification. Everything else — most competency pickers, and the ODCS admin bulk-upload — reads and writes a framework called kcmfinal_fw living inside knowledge-platform's generic, content-agnostic Framework/Term API instead. No code anywhere reconciles the two. Layered on top: a learner's acquired competencies live in a third store (one Cassandra table, written by two uncoordinated pipelines), and a fourth, public read-only copy exists in frac-dictionary, which mirrors frac-backend's Elasticsearch data directly without ever calling its REST API.

Honest gap: no code in any of these 13 repos moves data between frac-backend and the kcmfinal_fw mirror — whether they're meant to sync via something outside this trace, or have simply diverged, isn't answerable from source. Three closely-related repos — cbp-ai-service, ai-cbp-mdo-service, cbp-ai-ui — are deliberately not re-documented here; they're already covered by AI CBP Tool, which uses a third static copy of the vocabulary (a bundled dataset) to AI-generate Capacity Building Plans.
The real backend, found

frac-backend's FRACController implements the exact method names (addDataNode, searchNodes...) the gateway calls by name — closing what was an external gap, until it revealed a second one.

A two-tier review workflow, invisible elsewhere

L1 "technical review" then L2 "review board" gate every new/edited node — no other repo shows any awareness that competency data might be unverified.

ODCS writes to the mirror, not the real thing

The admin bulk-upload's "framework term create/publish" calls hit knowledge-platform's Framework API, never frac-backend — confirmed by an exhaustive search finding zero "framework"/"term" concepts in frac-backend's own code.

What it is

A Karmayogi joins a Community, posts a Question inside it, and other members answer with Answer Posts and nested Answer Post Replies — all three levels stored by one service (cb-discussion-service) in just two Postgres tables, discriminated by a type field. Bulk Registration
Uploading a CSV of new users to create many accounts at once — except the platform actually has three independent, largely disconnected implementations of this, and the backend endpoint named for "bulk create" creates exactly one user per call.
Route  Directory > Users > Bulk CreationLive endpoint  /v5/cb/user/bulkcreate✓ Verified from 8 repos · Sept 2026

What it is

An org admin uploads a CSV of new users from the Bulk Creation tab, completes an OTP challenge sent to their own email/phone, and the file is queued asynchronously. Behind that one upload, sunbird-cb-ext parses the file, tracks the batch, and — one HTTP call per row — calls sunbird-lms-service's /v5/cb/user/bulkcreate (or the NGO variant). A separate, self-contained CSV pipeline also exists natively inside sunbird-lms-service with no confirmed UI caller, and a fourth, legacy tenant-admin flow talks to Keycloak directly.

Honest gap: the two endpoints literally named "bulkcreate" create one user per call — there is no array-of-users handling in SSOUserCreateActor for either operation. The multi-row batching that makes this feature "bulk" happens entirely inside sunbird-cb-ext's Kafka consumer, a layer above the API most readers would assume does it.
Three unconnected implementations

A live pipeline through sunbird-cb-ext, a native but seemingly-unused pipeline inside sunbird-lms-service, and a legacy pipeline that talks to Keycloak directly — none share a Cassandra table or a Kafka topic.

"Bulk create" isn't bulk

/v5/cb/user/bulkcreate and /ngo/bulkcreate both take one flat user object and create exactly one account per HTTP call.

OTP protects the admin, not the new users

The verification step guards against an unattended session starting a bulk create — it says nothing about the rows in the file.

What it is

A Karmayogi earns points for logging in, enrolling, completing, rating and attending events, and can convert unconverted points into Karma Coins (up to 300 a month). Honest gap: the clients, not the processor, are the source of several displayed values — mobile and orgportal show 15 points for an ACBP course while the processor awards 5 + 5, and the mobile claim button hard-codes +10 against a processor claim of 5. See the As-Built tab.
One writer, many producers

Wallet is a Kafka round-trip

Two processors still deploy

V1 (seven topics) and V2 (one unified topic) both ship; which producers still feed V1 is not determinable from the code.

Organisation Hierarchy
How a ministry or state lays out the organisations under it as a tree, up to ten levels deep — edited node by node in a tree view or loaded in one go from a spreadsheet — so the rest of the platform can answer "who sits under whom".
Route  Directory > Organisation hierarchyLive endpoint  /organisation/v1/hierarchy/*✓ Verified from 9 repos · Oct 2026

What it is

Every root organisation (a ministry or a state) can own one hierarchy. An admin switches it on once from the hierarchy page, which gives the organisation an empty tree with ten named levels. From then on the tree is filled either one node at a time in the tree view — add a child, rename it, retire it, publish — or all at once by downloading a spreadsheet template, filling one row per path (L1 → L2 → L3 …, each cell written as Name<orgId>) and uploading it. The upload runs in the background; the admin polls a progress list and downloads the same sheet back with a Status and Error column per row. Separately, every new organisation created on the platform is dropped into its root's hierarchy automatically as a top-level node.

The non-obvious mechanism: a bulk upload does not edit the existing tree — it builds a fresh hierarchy copy, loads the rows into that, and if at least one row succeeded retires the previous hierarchy and points the organisation at the new one. The tree after an upload is exactly what the spreadsheet said; an upload where every row failed leaves the old tree untouched.
One tree per root, ten levels

A ministry or state owns the hierarchy; departments under it see their parent's tree. Levels are fixed at ten by configuration.

Two ways to fill it

Node-by-node in the shared tree view, or a spreadsheet upload validated row by row — chain gaps, unknown orgs, multiple parents, loops are all rejected with a per-row reason.

Never misses a new org

Creating an organisation anywhere on the platform also adds it to its root's tree as a top-level node, in the background.

How an admin experiences it

1 · OPEN

Hierarchy page resolves the root (own org, or the parent ministry/state for a department)

2 · CREATE

One click, first time only — the root now carries a hierarchy ID

3 · EDIT or UPLOAD

Work the tree view, or download the template (with a master list of orgs under the root) and upload it

4 · TRACK

Upload list shows INITIATED → IN_PROGRESS → SUCCESSFUL / FAILED with row counts

5 · FIX

Download the annotated sheet, correct only the failed rows, re-upload
