What it is

Every week, if a Karmayogi spends at least 60 minutes engaging with the platform, that week earns a “clap.” A small widget — on the web Home page, the web Profile page, and on mobile's Home screen, Your Activities and Achievement Hub — shows a running total and a four-week tick/cross strip. None of that arithmetic happens in any of the six repos analyzed: every client just asks one backend endpoint for “insights” and renders whatever comes back.

Honest gap: the backend only reads a Postgres learner_stats row and a 24-hour Redis cache — it never computes or updates a clap count. Nothing in sunbird-cb-ext, knowledge-platform-jobs, or sunbird-telemetry-service writes to that table. Whatever actually decides a user earned a clap lives outside every repo this documentation set covers.
Five implementations, one endpoint

Three on the web (one of them dead code), two on mobile — each independently fetches the same shape and renders its own card.

A 24-hour cache that can't tell “new” from “broken”

An empty result (no learner_stats row yet) is cached for the same 24 hours as a real one — a brand-new user looks identical to an outage.

The review-prompt isn't clap logic at all

Mobile's “rate us” popup after a clap is driven entirely by a server-issued feed item, not by any clap count the phone computes.
