What it is

A content partner is onboarded (directly by an admin, or self-registered then approved), its catalog is ingested by uploading an Excel/CSV file that a dedicated ingestion service transforms per-partner and indexes into its own store — entirely separate from the platform's native content graph. A curator reviews, competency-tags and publishes each course; a learner discovers it via a provider directory or a spotlight card, opens a dedicated CIOS detail page, and enrolls through a third, independent enrollment engine that enforces per-partner license caps before writing the enrollment.

Honest gap: no single service owns "is this user enrolled in this partner course." At least three independently-implemented enrollment/entitlement code paths exist — cb_external_enrollment_service (the one the UI actually calls), a parallel "external course" subsystem inside sunbird-course-service with its own Cassandra table, and the native Course enrollment pipeline underneath — with no code path found that calls between them.
Three separate content stores

cb-pores-service (partner master data), cios-content-service (ingested catalog) and cb_external_enrollment_service (a third local mirror) each keep their own copy of "CIOS content," with no shared code between them.

How a Karmayogi experiences it

1 · DISCOVER

Provider directory, or a home spotlight card into the see-all Providers tab

2 · VIEW

CIOS detail page, via the @sunbird-cb/collection-v2 library

3 · ENROLL

License-limit checks in cb_external_enrollment_service, then written

4 · PROGRESS

Synced back from the partner's own LMS via scheduler jobs or Kafka

5 · CERTIFY

Certificate + karma points, plus a separate badge-merge in course-service
