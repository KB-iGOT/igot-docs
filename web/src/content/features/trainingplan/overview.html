What it is

An MDO Admin or MDO Leader builds a plan in the Org Portal: a title, a set of courses (optionally flagged APAR — mandatory, performance-linked — and, within that, a "gating" subset required before a linked Comprehensive Assessment unlocks), a target audience picked through Reusable User Groups, and an end date. Publishing fans the plan out into per-assignee lookup rows so a Karmayogi's dashboard can find "plans that apply to me" without scanning every plan in the org. Underneath all of this, four independently-tabled generations of the same feature are simultaneously live today.

Honest gap: v1 (sunbird-cb-ext, table cb_plan), v2 (cb_plan_v2), and v3/v4 (cb_plan_v3, shared by both API versions) all still respond behind the same cbplan/* proxy path family — there is no migration path between them, and the Org Portal's own authoring service calls all four side by side.
Bespoke storage, repeated three times

Unlike Learning Pathway's generic-Content reuse, a Training Plan is its own Cassandra row — a decision made independently on v1, v2, and v3, each with its own table family, none retired.

A plan can gate a different feature entirely

The isApar flag and a Kafka-mirrored calinkedid turn an ordinary plan into an unlock gate for a Comprehensive Assessment — a real cross-feature dependency, not a metaphor.

How a Karmayogi experiences it

1 · AUTHORED

MDO Admin/Leader builds the plan: content, APAR/gating, audience, timeline

2 · PUBLISHED

Fans out into per-assignee lookup rows

3 · ASSIGNED

Karmayogi sees it in the cbp portal, bucketed Upcoming/Overdue/APAR/Completed

4 · GATES (optional)

Mandatory content can gate a linked Comprehensive Assessment

5 · OR BULK-GENERATED

An AI pipeline drafts and bulk-publishes designation-wide plans, independent of the above
